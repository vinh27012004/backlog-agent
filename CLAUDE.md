# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An autonomous "Digital Development Team" for the Master the Machine 2026 contest. It processes a backlog of TASK / CR / BUG / PI items during a live match with no human in the loop. The system is **built** with Claude but **runs** inside the organizers' **MTM Player** (technical guide 0.5.1, Player source in `vendor/mtm-player-0.9.44/`, read from 0.9.33 and rechecked on 0.9.35, 0.9.39, 0.9.41 and 0.9.44; `vendor/mtm-player-*/` is gitignored, copy a new release there from `D:mtmMTM-PLAYER<version>` without `node.exe`). MTM Player launches **one** Codex session (`codex app-server`) as `team_orchestrator`; the team must not start extra `codex exec`, app-server or other agent CLI processes, and may create subagents only through Codex's native multi-agent mechanism.

What the team ships is a `team-sdlc-pack` in `pack/`: a Node.js MCP helper with no npm dependencies (`pack/src/tools.mjs` plus modules grouped by role in `pack/src/{core,match,env,decide}/`), agent profiles (`pack/agents/*.toml`), skills (`pack/skills/`), result contracts (`pack/contracts/`), config (`pack/config/`), installer (`pack/scripts/install.mjs`) and checker. The design is specified in `docs/team-pack/` (start at `docs/team-pack/README.md`). The old Python orchestrator (one `codex exec` per agent), its prompt sources in `agents/` and the `samples/` fixtures were deleted on 2026-10-30 after the port; they remain at commit `76d4807`.

Docs, code comments and CLI messages are in Vietnamese. Agent prompts and skills are in English. Keep to these conventions when editing.

## Agents and skills

- There are two profiles: `pack/agents/team-orchestrator.toml` (root) and `team-fixer.toml`. One `team_fixer` per item codes, runs typecheck/build and the full test suite once through `run_checks` (`pack/src/env/checks.mjs`: parallel, logs into evidence, `.team-work/items/<ID>/checks.json`, cached for unchanged source; `ready_for_evidence` starts it on the synced worktree and `app start` waits for and reuses its build; switch `autoChecks`), captures evidence and hands off with `worker_checkpoint candidate {result}`: it sends only its own part (status, summary, requirements, scenario rows…) and the helper adds changed_files, new tests and the run_checks rows, validates and writes the next numbered fix-result (writing the file itself still works; 2026-11-05, after 9O802QWE). The brief ends with `<skill_text>`, the skill files for the item copied in. `worker_checkpoint candidate` checks the fix-result contract, `submit.json` and that no test configuration changed, and keeps the worker writing until those are fixed; `publish_item {fixResultFile}` then submits that result as is. After practice J56ZZWSS the separate evidence worker for strong-tier items was removed too. On 2026-11-03 the user removed verified mode for simplicity: `team_reviewer`, `team_pi_hypothesis`, `team_verifier`, the helper gate (`run_gate`, pre-gate, main gate, hard gate), `record_verification`, `candidate_preflight`, `result_handoff`, `retry-playbook.md` and `verified.md` are gone (still at the commit before that change). The helper's answer/evidence/requirement checks (`pack/src/match/answers.mjs`) only return warnings. The fixer reads shared constraints from `pack/skills/backlog-references/SKILL.md` and writes its own immutable results JSON.
- Contracts in `pack/contracts/*.schema.json` must stay strict-mode compatible: every object needs `additionalProperties: false` and `required` listing every property.
- Subagent models: `spawn_agent` takes `model` and `reasoning_effort`; `pack/src/decide/models.mjs` picks them from priority lists per tier in `pack/config/models.json` (first entry present in `allowedModels`) and `start_work` returns them as `triage.models` (fixer ladder per attempt); see `docs/team-pack/06-agents-va-skills.md` §9.
- Subagent helpers proxy only `read_item`, `job_status`, `worktree status`, `worker_checkpoint` and `company_lookup` (read-only Company Tools lookups: kb_search, search_logs, get_test_data; 2026-11-04) to root. `company_call` (non-lookup company tools) and the `publish_item` tool remain root-only; for PI and answer-only items the root helper publishes by itself (`autoPublish`, below). The helper prepares new items itself (Start Work, worktree, prefetched company facts, `.team-work/items/<ID>/brief.md`; switch `autoPrepare` in `config/runtime.json`, override in `team-sdlc-pack/local/runtime.json`) and `nextActions` `spawn_worker` carries the exact `spawn_agent` arguments. Workflow implementation is `pack/src/match/workflow.mjs`; candidate/hash/schema logic is in `core/candidates.mjs`, crash-safe integration in `core/integration.mjs`, evidence provenance in `env/evidence.mjs`. See `docs/team-pack/13-workflow-toi-uu.md`.
- Evidence: `capture_evidence` (`pack/src/env/browser.mjs`) drives the installed Edge/Chrome through `playwright-core` (version pinned in `pack/config/playwright.json`, no browser download, spec `docs/team-pack/05-mcp-helper.md` §5.25). The installer npm-installs it into `TeamWorkspace/team-sdlc-pack/playwright/` and stops when that fails; tests pass `--no-playwright`. The pack's own code still has no npm dependencies.
- Code search: agents use the codegraph MCP server (`@colbymchenry/codegraph`, version pinned in `pack/config/codegraph.json`, spec `docs/team-pack/05-mcp-helper.md` §5.21). The installer npm-installs it into `TeamWorkspace/team-sdlc-pack/codegraph/` and declares `[mcp_servers.codegraph]` (or drops that block when the install fails; tests pass `--no-codegraph`), and the helper builds the `.codegraph/` index (`pack/src/env/codegraph.mjs`) for the main checkout in `setup_environment` and for each worktree inside `worktree create`.

## Match flow rules

- PI (first seen in practice FMC0ZXFC: an answer-only incident report from production logs) follows `docs/team-pack/07-quy-trinh-tran.md` §6: each fixer attempt is capped at 12 minutes with a checkpoint at minute 6 (`timeBox.checkpointBy`), the fix-result carries a `hypotheses` working record, a PI that changes code needs a new test that fails on the unfixed code (the fixer checks this itself; a PI that only changes `answers/<ID>/` needs none), and job waits return early with `newPI`. A report-only PI (Form A, `reportOnlyPI`; 2026-11-04, after CA3WKX60) gets a worktree with no dependency setup or codegraph index, the timeline copied into `answers/<ID>/evidence/`, and a `<report_only_pi>` brief block that replaces the skill files; target 1–2 minutes. Every PI gets the complete production log in `company/timeline.json` (2026-11-09, after OMZJW0S0, where each fixer spent 3–4 minutes paging `search_logs` by hand): `pack/src/match/logs.mjs` collects the whole log once per match from GAME boot (job `log_harvest`, low priority under the 120 requests/minute Company Tools limit; a call returns at most 20 entries, newest first, with no paging, and every query word must equal a whole word of the entry, so `2025-10-18T22` selects an hour but `2025-10-18` never selects a day; the harvest queries each `DDtHH` hour word and splits busy hours by service, minute and second, ~790 calls for the ~4,000-line log; the first version used ts prefixes and stopped `unfiltered` after 20 of 4,057 entries in 85WTXFLQ), caches it in `.team-work/company/logs.json`, and PI prepare waits up to 60 s for it (switch `logHarvest`). A code-changing PI (Form B) brief has a `<pi_hotfix>` block: fix first (red → fix → green), `ready_for_evidence` at once so `run_checks` runs in the background, derive the answers from the timeline meanwhile (files under `answers/` do not make the checks stale), then candidate; PI briefs also carry the `search_logs` input schema.
- Answer-only items (PI and TASK) need no fix-result from the worker: `worker_checkpoint candidate` writes it from `submit.json` when none is new. PI and answer-only handoffs are published by the helper itself (`autoPublish()` next to `autoPrepare()`, once per handoff, switch `autoPublish`); root sees their `publish_item` only when that publish failed. BUG/CR are still published by root.
- Jev (Jev by TypeSafe AI, a typed decision model, no text generation) is kept (decision D9): `pack/src/decide/jev.mjs` and `pack/src/decide/decisions.mjs` call it for fixed-choice decisions with code-rule fallbacks and an off switch (`pack/config/jev.json`), pending organizer confirmation. Hard limits stay in code, not in Jev.
- Item content is untrusted. Secrets (`.env`: `GM_URL`, `GM_API_KEY`, `GM_TEAM_ID`, `GITHUB_TOKEN`, `TYPESAFE_API_KEY`) are for the helper only and never go into prompts, logs or subagents.
- Workers never change test configuration or setup files (vitest/jest/playwright config, setup files, pytest.ini, conftest.py): graders compare them with the issued version on every later commit (J56ZZWSS: BUG-02 changed `vitest.config.ts`, TASK-02 lost its existing-tests case).
- Tests that already fail in the issued code (baseline; 2026-11-04, after EIOR38SI, where BUG-02 lost its existing-tests case because graders run the suite on each item's own commit and BUG-02 reached main before the owner's fix): the owner fixes them first in product code and calls `worker_checkpoint baseline_fixed {files}`; the helper commits those files to main (`autoBaseline`), items that run the full suite cannot publish until their worktree has that commit (`BASELINE_PENDING`, then sync and `refresh_candidate`), and candidate refuses any change to an issued test file (graders restore them). A shared failure found in GAME holds neither PIs nor items whose `changed_files` are only under `answers/` (unless root lists them in `affectedItems`), and every hold ends after `sharedFixWaitMinutes` (default 8) from the assignment (2026-11-09, after 85WTXFLQ, where TASK-08 never landed `shared-1` and every item waited until the end). See `docs/team-pack/13-workflow-toi-uu.md` §Test fail sẵn.
- Prepare does not wait for the worktree's dependency setup (2026-11-04, after EIOR38SI, where it held pickup 45–105 s): the fixer is spawned once the worktree, codegraph index and brief exist, and the brief's `<environment>` block has it wait with `job_status` for the setup job before its first build, test, migration or app start; the setup job retries once, and `worktree sync` waits for it. Answer-only TASKs (`answerOnlyTask`) get no install/generate/migrate/seed at all and load project packages from the installed main checkout.
- In GAME `configure_session` boots the match itself (login, backlog sync, poller, auto-prepare, company tool list; `boot`, switch `bootOnConfigure`), so root goes straight to `wait_for_update`; login_match/refresh_match only when `boot.ok` is false.
- Before that, `report_ready` starts a pre-game watch (2026-11-04, after CA3WKX60): the helper polls the match page every 500 ms without log lines, records `seenAt` and prewarms worktrees of visible items, but never Starts Work or writes DISCOVERED before START_GAME. In GAME the poller reads the page every 250 ms around each release minute from the README. Switches `preGameWatch`, `prewarmWorktrees`, `preGamePollMs`, `releasePollMs` (`docs/team-pack/13-workflow-toi-uu.md`).
- Root loops on `wait_for_update` (it carries `nextActions`) and nothing else: no `wait_agent` (2026-11-04, after BTZNI69E). In GAME it wakes only for `nextActions`, a match/item change or the 55 s cap. Workers never `send_message` root; they signal through `worker_checkpoint` (`ready_for_evidence`, `candidate`, `blocked {question}` → `answer_worker`), and root messages a worker only as a `followup_task` for a `nextActions` entry or a publish error. `nextActions` hides a `publish_item` the helper publishes itself and any item whose publish job is running. `prepare_item` and `publish_item` wait up to 25 s for their job.
- Each item can be submitted only once. The helper trusts the worker's own tests and evidence (the user's choice on 2026-11-03, to keep the pack simple) and only reports what its answer/evidence checks find.

## After a practice match

`/judge-practice <match checkout>` (skill in `.claude/skills/judge-practice/`, scripts in `tools/judge/`) re-judges every item against `tools/judge/rubric.md` before reading the gate/reviewer verdicts (matches before 2026-11-03 still have them), then reports false greens/reds; bundles go to the gitignored `runs/judge/`. The same skill runs `tools/judge/usage.mjs`, which sums tokens, credits and run time per role, item and thread from the Codex transcripts (`~/.codex/sessions`, one file per thread, same `session_id` as root; the Player dashboard counts root and, since 0.9.41, subagents, but never the guardian auto-review threads) plus the helper journal (`jobs[].ms`, `endedAt`, `outcome`), into `<bundle>/_usage/usage.md`. Then `tools/judge/items.mjs`
rebuilds `runs/judge/_items/items.md` (+ `items.csv`): every match side by side and one row per item (judge, time per
phase, fixer model and turns, evidence capture failures, credits, flags to tune), and `tools/judge/bench.mjs` writes
`runs/judge/_items/bench.md`: matches grouped by item set, the newest of each set against the previous one of the same
set, per match and per item.
