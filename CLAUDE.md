## What this is

An autonomous "Digital Development Team" for the Master the Machine 2026 contest. It processes a backlog of TASK / CR / BUG / PI items during a live match with no human in the loop. The system is **built** with Claude but **runs** on **Codex CLI** (`codex exec`, verified against codex-cli 0.162.1 and 0.163.0). Each "agent" is one `codex exec` call. The Python orchestrator decides which agent to call, builds its prompt, and reads back JSON that a schema forces into shape.

**JEV is not a Codex agent.** It is **Jev by TypeSafe AI**, a typed decision model (no text generation) that the orchestrator calls over HTTP for fast fixed-choice decisions. There is no separate analysis agent: the fixer analyses the item itself in its first step.

Docs, code comments and CLI messages are in Vietnamese. The agent prompts under `agents/` are in English. Keep to these conventions when editing.

## Commands

The code needs **Python 3.11+** (`tomllib`). On this machine the default `python` is 3.10, so use `py -3.13`.

```bash
py -3.13 -m unittest discover -s tests -v                    # all tests (cost nothing)
py -3.13 -m unittest discover -s tests -k test_route_pi_never_reviews   # one test (by name or class, e.g. -k ProfileTest)

py -3.13 -m orchestrator.cli profile D:/path/to/repo          # detect stack -> project profile JSON
py -3.13 -m orchestrator.cli prompt fixer --item samples/items/BUG-07.json --repo D:/path/to/repo   # print prompt, no $
py -3.13 -m orchestrator.cli agent fixer --item samples/items/BUG-07.json --mock   # replay mock output, no $
py -3.13 -m orchestrator.cli decide triage --item samples/items/PI-03.json --mock  # Jev decision with fake answers, no API call
py -3.13 -m orchestrator.cli match --mock --jev-mock --until-idle   # whole fake match on the sample repo, no $
py -3.13 -m orchestrator.cli monitor                         # serve the latest match's DB at http://127.0.0.1:8765
py -3.13 -m orchestrator.cli gate --item samples/items/BUG-07.json --workdir D:/path/to/worktree --fix-result runs/BUG-07/fixer-1.last.json   # real build/test, no $
py -3.13 -m orchestrator.cli runs                             # per-role run stats from runs/state.db
```

`python -m unittest tests.test_agents` does not work, because `tests/` has no `__init__.py` and the name clashes with an installed `tests` package. Use `discover -k` instead.

Known on Windows: `LiveRunWithFakeCodexTest` is skipped because the fake codex is a shebang script. Tests that open a `Store` must close it (use `with Store(...) as store:`), or Windows cannot delete the temp dir because the SQLite file is still locked.

A live Codex run costs real money from a fixed $50 budget. It needs `codex` on PATH, a Codex login, and `--workdir` pointing at the target repo. By default the runner does **not** set `CODEX_HOME` (`codex_home = ""` in `config/agents.toml`), so Codex uses the machine's standard environment: the organizers' login and the MCP tools that come with the contest source. `build_command()` adds what must hold regardless via `-c`: the `*KEY*`/`*TOKEN*`/`*SECRET*` env exclude, and on Windows `windows.sandbox="elevated"` (without it `codex exec` rejects every shell command and the agent only talks). Setting `codex_home = "config/codex-home"` brings back the team config (login in its gitignored `auth.json`); Codex then appends `[projects.'<path>'] trust_level` blocks to that `config.toml` for each new repo, so strip them before committing. A one-item live check: `cli match --scenario samples/scenarios/single-bug.json --speed 1 --poll 5 --max-attempts 1 --until-idle --workers 1` (fixer + reviewer, about 3 minutes). A live Jev call needs `TYPESAFE_API_KEY` in the environment. Don't start live runs unless asked; use `--mock` or the `prompt` subcommand.

## Architecture

**Agent pipeline** (`orchestrator/`):
- `config.py`: loads `config/agents.toml`. A role's settings are `[defaults]`, then `[roles.<name>]`, then `[roles.<name>.by_type.<TYPE>]`, then `[tiers.<tier>]` (model + effort, only when a tier is passed), later entries winning. `small`/`strong` are labels that `Decider.route()` asks Jev to pick; Jev has no such modes itself. `item_type()` takes the type from the ID prefix (`BUG-07` gives `BUG`); this step never uses an LLM.
- `prompt.py`: `build_prompt()` puts the static parts first so the API prompt cache works: `rules/common.md`, then role, skill (fixer and reviewer only, picked by item type), references (`bug-patterns` for fixer BUG, `pi-triage` for fixer PI and pi-hypothesis, `retry-playbook` when there is a previous attempt), stack packs, and project profile. The parts that change come after: item_meta, triage, fix_result, item, other_items, diff, gate_report, previous_attempt, hypothesis. Untrusted data is wrapped by `_fence()`, which escapes closing tags to block prompt injection.
- `profile.py`: pure-code stack detection (java/node/python/dotnet/go/php; monorepos give several stacks). It produces the build, test_all, test_one (`{target}` placeholder) and run_app commands, plus `forbidden_skip` markers for the gate. Adding a stack takes `agents/stacks/<id>.md` plus a detector added to `DETECTORS`.
- `agents.py`: `AgentRunner.run()` builds the command with `build_command()` (`--json --strict-config --ephemeral -s <sandbox> --output-schema ... -o ... -`, prompt on stdin), runs it with a timeout kill, streams JSONL through `events.feed()`, then checks the final message with `validate_output()`. A run that fails on a Codex account error (quota or rate limit, matched by `events.limit_kind()`) gets status `limited` with `limit` set, not `failed`. Modes: `live` or `mock`. Mock replays `<mock_dir>/<role>/<ITEM>-<attempt>.jsonl`, then `<ITEM>.jsonl`, then `default.jsonl`, and `git apply`s `<ITEM>-<attempt>.patch` or `<ITEM>.patch` into the workdir if present, so a mock fixer really changes files. Every run writes `<runs_dir>/<item>/<role>-<attempt>[-<label>].{prompt.md,jsonl,last.json}` and a row in SQLite (`label` separates parallel runs, e.g. PI hypotheses).
- `events.py`: parses the `codex exec --json` event stream (`thread.started`, `item.completed`, `turn.failed`, `error`, plus legacy pre-0.44 names) into trace events. `Reconnecting...` errors are left out of the trace.
- `gate.py`: `Gate(profile).run(item, worktree, fix_result)` re-checks the fix outside the sandbox, cheapest first and stopping at the first failure: diff (non-empty, under `config/gate.toml` limits), forbidden changes (skip markers in test files, deleted tests, fewer assertions, build files without `needs_dependency`, CI), build, the agent's `tests_added` through `test_one` (one rerun to rule out flakiness), `test_all`, then MVS if a command is given. It returns a `GateReport` whose `fail_kind` matches `agents/references/retry-playbook.md`, with `to_text()` for the reviewer and `previous_attempt()` for a retry. Agent-declared test names are filtered by `SAFE_TARGET` before going into a shell command, and secret env vars are stripped. Command logs go to `runs/<item>/gate-<attempt>-<check>.log`.
- `logs.py`: Log Condenser. `signature()` gives `<Exception>@<first project frame>` or `compile:<file>:<msg>`, without line numbers or the worktree path, so it stays the same across attempts; `condense()` keeps the failure lines.
- `match.py`: `MatchRunner.run()` is the main loop. It polls the Game Master, triages new items, queues them (PI first, then nearest deadline, severity, easiest) and runs each item, in a thread pool of `workers` or inline when `workers = 0`: start → `route()` (tier, reviewer) → up to `max_attempts` × [fixer → gate → reviewer → `next_action`] → `safe_submit` or drop. Minutes left are re-read from the server after the fixer and gate. The same error signature a second time sets `same_signature_as_before` in `previous_attempt`; a third time drops the item. A PI that fails the gate gets `pi_hypotheses` read-only checkers in parallel, and their verdicts go to the next fixer as `hypothesis`. A reviewer `high` issue triggers a retry, except on the last chance, where the gate-passing version is submitted. A `limited` fixer run does not count as an attempt: the item waits `limit_wait_sec` and reruns, and no new item is dispatched while any item is waiting (`codex_limit` goes to `match_state` for the monitor banner). Before submitting, `_publish()` commits the worktree and pushes the sha to `push_remote` branch `push_branch` (must contain `{item}`); the sha goes into the payload as `gitRevision`, and a failed push means no submission. Settings in `config/run.toml`. Items already `submitted`/`dropped` in the `items` table are skipped, so a restarted run resumes.
- `workspace.py`: `Workspaces` gives each item a detached git worktree at a pinned base sha, reset with `reset --hard` + `clean -fd` before each attempt. `commit()` commits the item's changes (agents never commit); `push()` never forces: if the branch already points elsewhere (a rerun after a crash) it pushes to `<branch>-<sha8>` so a sha that was already submitted stays on the remote. `init_sample_repo()` turns `samples/repo-template/` (a small Python shop whose bugs and gaps match `samples/items/`) into a git repo for fake matches; with `bare_remote` it also creates a bare repo as `origin` so fake matches push for real.
- `monitor.py`: `snapshot(db)` reads a match DB read-only (tolerates older DBs missing tables) and returns items with state, phase, minutes left from `match_state`, last gate checks, review, fixer summary, submission and a merged trace, plus recent events and Jev/agent stats. `make_server()`/`serve()` bind 127.0.0.1 and serve only `index.html`, `data.js` and `/api/state`. `monitor/index.html` polls `/api/state` every 3 s when served, and falls back to `window.MONITOR_DATA` in `monitor/data.js` when opened as a file; regenerate that sample with `cli monitor --db <state.db> --export monitor/data.js`.
- `gamemaster.py`: `GameMasterClient` ABC (`server_time`, `get_match`, `get_item`, `start_item`, `submit`), errors, `with_retry()` and `safe_submit()`. The fake lives outside the orchestrator in the top-level package `fake_gamemaster/` (imported only by `cli match` and tests): `FakeGameMaster` plays a JSON scenario (`samples/scenarios/practice.json`) on a `FastClock(speed)` or a test `ManualClock`, with pauses that freeze deadlines, items without `deadline_min` (`ItemInfo.deadline_min = None`; `minutes_left` is always capped at the match end), the submit rules (`Rejected` codes `NOT_STARTED`, `ALREADY_SUBMITTED`, `CLOSED`, `MATCH_NOT_RUNNING`) and `fail_next(method, applied=...)` to simulate a network error before or after the server acts. `safe_submit()` writes `submitting` to SQLite before calling the API and, on a network error, asks the server for the item's state instead of submitting again. Only reads go through `with_retry()`; `submit` is never retried blindly. `HttpGameMaster` waits for the organizers' API docs.
- `store.py`: SQLite (`runs/state.db`) with tables `agent_runs`, `agent_events`, `jev_decisions`, `gate_runs` (`gate_history()` for repeated-signature checks), `submissions` (one row per item) and `items` (state per item for the monitor and for resuming) and `match_state` (one row per poll: match status, server-clock minutes left per item, `max_attempts`, `codex_limit`). One connection is shared by all threads behind an `RLock`; `cli match` uses a fresh DB per match at `runs/<match>/state.db`. The monitor will read from it. `Store` is a context manager; call `close()` when done.

**Jev decisions** (`orchestrator/jev.py`, `orchestrator/decisions.py`, `config/jev.toml`):
- `jev.py`: `JevClient` posts to `{base_url}/v1/systemone` with typed questions built by `noul()` (yes/no), `choice()` and `score()`. It uses only the standard library and wraps every failure in `JevError`. Without `TYPESAFE_API_KEY` or with `enabled = false`, `available` is false.
- `decisions.py`: `Decider` holds the decision points: `triage` (severity, difficulty, injection, module), `related`, `route` (fixer tier `small`/`strong`, reviewer yes/no), `claims_supported`, `root_cause_confirmed`, `next_action` (submit/retry/drop). Each one asks Jev first and falls back to a code rule on error or below the thresholds in `config/jev.toml`. Every decision is recorded in `jev_decisions`. `mock_transport` gives deterministic fake answers.
- Hard limits stay in code, not in Jev: `next_action` only offers actions that are valid (never `submit` when the gate failed), PI never gets a reviewer, and the injection check counts as "yes" when the regex heuristic matches even if Jev says no.

**Agents** (`agents/`, see `agents/README.md` for the full table): roles `fixer` (fix-result, workspace-write), `reviewer` (review, read-only) and `pi_hypothesis` (hypothesis, read-only, runs 2–3 in parallel when a PI is stuck). The role key in the config is `pi_hypothesis`; its prompt file is `roles/pi-hypothesis.md`. The fixer returns its own analysis in `criteria` and `suspects`.

**Schemas** (`agents/schemas/*.schema.json`) must stay strict-mode compatible: every object needs `additionalProperties: false` and `required` listing every property. `SchemaTest` enforces this and expects exactly 3 schemas.

**Design rules that shape the code** (from `docs/legacy/ARCHITECTURE.md`):
- The orchestrator does **not** read tokens or compute cost, because the organizers' Codex plugin does that. A test asserts that results have no `cost_usd`.
- Skills are injected into the prompt by code and never written to the contest repo as `AGENTS.md` or `.agents/`, which would pollute the submitted diff.
- Item content is untrusted. The Codex sandbox has no network. `config/codex-home/config.toml` strips `*KEY*`/`*TOKEN*`/`*SECRET*` env vars from shell commands and disables browser, computer-use, plugins and similar features. Secrets in `.env` (`GM_URL`, `GM_API_KEY`, `GM_TEAM_ID`, `GITHUB_TOKEN`, `TYPESAFE_API_KEY`; template in `.env.example`) are for team control code only and never go into prompts or logs.
- Each item can be submitted only once, so the orchestrator must re-run the gate itself rather than trust the agent's output.

**Mock data**: `samples/build_mocks.py` writes `samples/mock/fixer/<ITEM>.{patch,jsonl}` from fixes applied to the sample repo; rerun it after changing `samples/repo-template/`. `.gitattributes` keeps `*.patch` and the template as LF, otherwise `git apply` fails on Windows with `core.autocrlf=true`. In `tests/test_match.py` the `Harness` copies the mocks and swaps in variants (a wrong patch for attempt 1, a `request_changes` review) to reach each branch of the loop.

**Not built yet**: the MVS runner (the gate only takes an MVS command), lint/scan in the gate, and checking that a reproduction test fails on the original code; submit template (`template_answers`), `already_fixed`, screenshot evidence, watching items for content changes, `max_points` in the queue, polling grader results, `ready()`, a watchdog (see `docs/legacy/ARCHITECTURE.md` §11, items 4g–4i); the `related` decision is not used by the loop yet; MCP servers (`codegraph`, `runner`, `web`; declared in `config/codex-home/config.toml` with `enabled = false`), the MCP `control` server (the loop runs as a CLI for now), `HttpGameMaster`. See the roadmap in `docs/legacy/ARCHITECTURE.md` §11.

`config/codex-home/` is gitignored except `config.toml`. Codex writes sessions and auth there.
