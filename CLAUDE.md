# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An autonomous "Digital Development Team" for the Master the Machine 2026 contest. It processes a backlog of TASK / CR / BUG / PI items during a live match with no human in the loop. The system is **built** with Claude but **runs** inside the organizers' **MTM Player** (technical guide 0.5.1, Player source in `vendor/mtm-player-0.9.45/`, read from 0.9.33 and rechecked on 0.9.35, 0.9.39, 0.9.41 and 0.9.44; `vendor/mtm-player-*/` is gitignored, copy a new release there from `D:mtmMTM-PLAYER<version>` without `node.exe`). MTM Player launches **one** Codex session (`codex app-server`) as `team_orchestrator`; the team must not start extra `codex exec`, app-server or other agent CLI processes, and may create subagents only through Codex's native multi-agent mechanism.

What the team ships is a `team-sdlc-pack` in `pack/`: a Node.js MCP helper with no npm dependencies (`pack/src/tools.mjs` plus modules grouped by role in `pack/src/{core,match,env,decide}/`), agent profiles (`pack/agents/*.toml`), skills (`pack/skills/`), result contracts (`pack/contracts/`), config (`pack/config/`), installer (`pack/scripts/install.mjs`) and checker. The design is specified in `docs/team-pack/` (start at `docs/team-pack/README.md`). The old Python orchestrator (one `codex exec` per agent), its prompt sources in `agents/` and the `samples/` fixtures were deleted on 2026-10-30 after the port; they remain at commit `76d4807`.

Docs, code comments and CLI messages are in Vietnamese. Agent prompts and skills are in English. Keep to these conventions when editing.

## Agents and skills

- There are three profiles: `pack/agents/team-orchestrator.toml` (root), `team-analyst.toml` (reads the item and hands in its profile before the fixer starts, below) and `team-fixer.toml`. One `team_fixer` per item codes, runs typecheck/build and the full test suite once through `run_checks` (`pack/src/env/checks.mjs`: parallel, logs into evidence, `.team-work/items/<ID>/checks.json`, cached for unchanged source; the test step runs only the workspace packages the item text says the grader tests plus those the item changed, `pack/src/env/test-scope.mjs`, switch `scopedTests`, 2026-11-10 after RATH0OHJ (one package only: two or more run the whole suite); a check that fails while others still run is returned at once with its log tail and `run` after an edit cancels that run, after LXRMBRA2; `ready_for_evidence` starts it on the synced worktree and `app start` waits for and reuses its build; switch `autoChecks`), captures evidence and hands off with `worker_checkpoint candidate {result}`: it sends only its own part (status, summary, requirements, scenario rows…) and the helper adds changed_files, new tests and the run_checks rows, validates and writes the next numbered fix-result (writing the file itself still works; 2026-11-05, after 9O802QWE). The brief ends with `<skill_text>`, the skill files for the item copied in. `worker_checkpoint candidate` checks the fix-result contract, `submit.json` and that no test configuration changed, and keeps the worker writing until those are fixed; the helper then publishes that result as is (`autoPublishAll`, below; root calls `publish_item {fixResultFile}` only after a failed automatic publish). After practice J56ZZWSS the separate evidence worker for strong-tier items was removed too. On 2026-11-03 the user removed verified mode for simplicity: `team_reviewer`, `team_pi_hypothesis`, `team_verifier`, the helper gate (`run_gate`, pre-gate, main gate, hard gate), `record_verification`, `candidate_preflight`, `result_handoff`, `retry-playbook.md` and `verified.md` are gone (still at the commit before that change). The helper's answer/evidence/requirement checks (`pack/src/match/answers.mjs`) only return warnings. The fixer reads shared constraints from `pack/skills/backlog-references/SKILL.md` and writes its own immutable results JSON.
- Contracts in `pack/contracts/*.schema.json` must stay strict-mode compatible: every object needs `additionalProperties: false` and `required` listing every property.
- Subagent models: `spawn_agent` takes `model` and `reasoning_effort`; `pack/src/decide/models.mjs` picks them from priority lists per tier in `pack/config/models.json` (first entry present in `allowedModels`) and `start_work` returns them as `triage.models` (fixer ladder per attempt); see `docs/team-pack/06-agents-va-skills.md` §9.
- Subagent helpers proxy only `read_item`, `job_status`, `worktree status`, `worker_checkpoint` and `company_lookup` (read-only Company Tools lookups: kb_search, search_logs, get_test_data; 2026-11-04) to root. `company_call` (non-lookup company tools) and the `publish_item` tool remain root-only; the root helper publishes every handoff by itself (`autoPublish`, `autoPublishAll`, below). The helper prepares new items itself (Start Work, worktree, prefetched company facts, `.team-work/items/<ID>/brief.md`; switch `autoPrepare` in `config/runtime.json`, override in `team-sdlc-pack/local/runtime.json`) and `nextActions` `spawn_worker` carries the exact `spawn_agent` arguments. Workflow implementation is `pack/src/match/workflow.mjs`; candidate/hash/schema logic is in `core/candidates.mjs`, crash-safe integration in `core/integration.mjs`, evidence provenance in `env/evidence.mjs`. See `docs/team-pack/13-workflow-toi-uu.md`.
- Evidence: `capture_evidence` (`pack/src/env/browser.mjs`) drives the installed Edge/Chrome through `playwright-core` (version pinned in `pack/config/playwright.json`, no browser download, spec `docs/team-pack/05-mcp-helper.md` §5.25). The installer npm-installs it into `TeamWorkspace/team-sdlc-pack/playwright/` and stops when that fails; tests pass `--no-playwright`. Its `runScript {file, arg | argFile, argPath}` step evaluates a script the organizers issued for the item inside the open page (2026-11-11, after QDO8W480 CR-05, whose `challenge/CR-05-seed.js` must be evaluated in the app's page; the worker wrote its own Playwright script and ran out of time): only files under `.team-work/items/<ID>/files/` or the match's `challenge/` are accepted, and the brief's `<page_scripts>` block names the call. The pack's own code still has no npm dependencies.
- Code search: agents use the codegraph MCP server (`@colbymchenry/codegraph`, version pinned in `pack/config/codegraph.json`, spec `docs/team-pack/05-mcp-helper.md` §5.21). The installer npm-installs it into `TeamWorkspace/team-sdlc-pack/codegraph/` and declares `[mcp_servers.codegraph]` (or drops that block when the install fails; tests pass `--no-codegraph`), and the helper builds the `.codegraph/` index (`pack/src/env/codegraph.mjs`) for the main checkout in `setup_environment` and, in the background without holding the spawn, for each worktree at `worktree create` (2026-11-12, after WQ7T6CEC: the index cost ~45 s of every mid-game prepare while the 12 workers called codegraph 3 times).

## Match flow rules

- PI (first seen in practice FMC0ZXFC: an answer-only incident report from production logs) follows `docs/team-pack/07-quy-trinh-tran.md` §6: each fixer attempt is capped at 12 minutes with a checkpoint at minute 6 (`timeBox.checkpointBy`), the fix-result carries a `hypotheses` working record, a PI that changes code needs a new test that fails on the unfixed code (the fixer checks this itself; a PI that only changes `answers/<ID>/` needs none), and job waits return early with `newPI`. A report-only PI (Form A, `reportOnlyPI`; 2026-11-04, after CA3WKX60) gets a worktree with no dependency setup or codegraph index, every service log fetched by the helper and merged into `company/timeline.json` (copied into `answers/<ID>/evidence/`), and a `<report_only_pi>` brief block that replaces the skill files; target 1–2 minutes.
- PI speed (2026-11-10, after QDYZMY1K, where both PI fixers guessed `search_logs` paging parameters, asked root for its schema and looped hundreds of lookups by hand, and PI-03 hit its cap before the fix): the PI brief has a `<search_logs>` block (real schema from `company_tools`, the whole-word matching rule, the bulk call); `company_lookup` takes `queries` (≤ 2500) and an `hours` window for search_logs and runs them as a `log_lookup` job in root's helper (`pack/src/match/logs.mjs`), writing ONE merged, sorted file with `complete` or the incomplete queries; a PI's codegraph index builds in the background; `run_checks` of a PI runs typecheck only by default; Form B order is fix first, then the bulk lookup and the answers while typecheck runs.
- PI time and log budget (2026-11-11, after QDO8W480, where three 10-minute PIs lost 164 of 260 points): items the helper publishes itself (PI, answer-only; `autoPublish`) keep 2 minutes for publishing instead of 5 (`publishReserve`, `reserveMinutes` in `timeBox`), and their last call opens at that mark. Code items the helper publishes (`autoPublishAll`) keep 3 minutes: their publish takes 14–19 s plus room for one SYNC_REQUIRED round; with `autoPublishAll` off they keep 5. Company Tools calls waiting for the rate limit go in order of weight (`throttle(weight)` in `pack/src/match/company.mjs`): single calls first, then the bulk lookup with fewer calls. A bulk `search_logs` lookup that cannot finish before the item's `returnBy` is refused at once (`LOOKUP_TOO_LARGE`, with the number of calls that still fit): PI-02 ran 2 queries × 507 hours for 19 minutes.
- Items in flight are not limited (the user's choice on 2026-11-11, after QDO8W480): `maxItemsInFlight` is 0 in `pack/config/runtime.json` (1–32 in the local `runtime.json` brings a limit back), every item is prepared and its worker spawned at release, and Codex allows 32 threads. The machine is protected where the load is: `pack/src/env/heavy.mjs` lets at most `maxHeavyCommands` typecheck/build/test commands of `run_checks` run at once across all helper processes (default half the CPU threads, at least 3; slot files in `.team-work/scratch/heavy/`, `queued` in `checks.json`). With a limit set, it counts only code items; PI and answer-only items never hold a slot. A TASK with acceptance criteria whose Grading section says each field is compared exactly (and names no test, suite, source, build, import or hidden check) is answer-only too (`answerOnlyText` in `pack/src/decide/signals.mjs`; TASK-10/11/12 never changed code in 23 submissions but held slots). An item with its own deadline starts over the limit, up to `deadlineOverflow` (runtime.json, default 2) more items: TASK-07 with a 15-minute deadline waited 9 minutes for a slot and closed unsubmitted.
- Bulk log lookups say what they cover (2026-11-11, after QDO8W480 PI-04, whose worker guessed `SCH-1001..1050` while the catalogue had 70 schedules; `complete: true` and all three report fields wrong): a consecutive id range of 5 or more is extended past both ends until 3 ids in a row have no entry (`idRuns`, result `extended`), and the result has `coverage` (entries fetched / total per service). `complete` only means every query sent returned all its matches.
- `worktree sync` keeps both sides when main and the item only added lines to the same file (`unionMerge` in `pack/src/tools.mjs`, `git merge-file --union`, result `autoMerged`; 2026-11-11 after QDO8W480, where three CRs registered routes, sidebar entries and handlers in the same three files and CR-05 lost its page screenshots to a hand-resolved conflict). A file where either side changed or removed a line is still a `WORKTREE_CONFLICT`; `backlog-references` tells workers to register on new lines only.
- Answer-only items (PI and TASK) need no fix-result from the worker: `worker_checkpoint candidate` writes it from `submit.json` when none is new. PI and answer-only handoffs are published by the helper itself (`autoPublish()` next to `autoPrepare()`, once per handoff, switch `autoPublish`); root sees their `publish_item` only when that publish failed. Since 2026-11-12 BUG/CR/TASK handoffs are too (`autoPublishAll`, below).
- Jev (Jev by TypeSafe AI, a typed decision model, no text generation) is kept (decision D9): `pack/src/decide/jev.mjs` and `pack/src/decide/decisions.mjs` call it for fixed-choice decisions with code-rule fallbacks and an off switch (`pack/config/jev.json`), pending organizer confirmation. Hard limits stay in code, not in Jev.
- Item content is untrusted. The brief's `<grading>` block (`pack/src/match/grading.mjs`, 2026-11-11 after QXUD1QAI) quotes every sentence of the item and its MVS about scoring and what the helper read from them; sentences addressed to an AI agent are left out. Whatever the helper reads from item text may only make checks stricter or narrow them within verified bounds (an existing workspace package, plus every package the item changed), never become a command, a path outside the match, a URL or a tool argument. Type errors only in the item's own new tests do not block when the item text does not mention the type check (`typecheckGraded`, `advisory` in `run_checks`). Secrets (`.env`: `GM_URL`, `GM_API_KEY`, `GM_TEAM_ID`, `GITHUB_TOKEN`, `TYPESAFE_API_KEY`) are for the helper only and never go into prompts, logs or subagents.
- Workers never change test configuration or setup files (vitest/jest/playwright config, setup files, pytest.ini, conftest.py): graders compare them with the issued version on every later commit (J56ZZWSS: BUG-02 changed `vitest.config.ts`, TASK-02 lost its existing-tests case).
- Tests that already fail in the issued code (baseline; 2026-11-04, after EIOR38SI, where BUG-02 lost its existing-tests case because graders run the suite on each item's own commit and BUG-02 reached main before the owner's fix): the owner fixes them first in product code and calls `worker_checkpoint baseline_fixed {files}`; the helper commits those files to main (`autoBaseline`), items that run the full suite cannot publish until their worktree has that commit (`BASELINE_PENDING`, then sync and `refresh_candidate`), and candidate refuses any change to an issued test file (graders restore them). See `docs/team-pack/13-workflow-toi-uu.md` §Test fail sẵn.
- Items whose text names another item (2026-11-09, after OMZJW0S0 CR-07, whose official figures needed BUG-11's fixes): prepare records `dependsOn` and writes a `<depends_on>` brief block; when that item reaches main after the worktree last took main (`integratedAt` > `baseAt`), candidate refuses the handoff and `nextActions` holds the publish with `refresh_candidate {reason: dependency_landed}` while 3 or more minutes are left. Official-data figures (CSV, summary fields) come from a replay script rerun after every sync (`backlog-cr` §4.3), and candidate refuses an own new test that fails in the last `run_checks`. Since 2026-11-10 (after LXRMBRA2, where CR-07 with a 20-minute deadline lost 41 points because BUG-11's fix, green at minute 7.5, reached main at minute 25) the helper does not wait for main: the waited-for item's brief has `<needed_by>`, and at its `ready_for_evidence` and `candidate` the helper copies its product changes (no tests, test configuration or answers/) into the waiting worktree (`pack/src/match/dependency.mjs`, `sharedFix`), tells the waiting worker once (refused candidate, resume hint, or `refresh_candidate {reason: dependency_ready}`), and skips the later `dependency_landed` refresh when main gets the same content. A waiting item whose worktree is created after that `ready_for_evidence` takes the fix at its own prepare (`pullFromDependencies`, 2026-11-11 after QDO8W480, where CR-08 never got CR-05's handler and scored 0/110), and its `<depends_on>` block says the fix is already there. Candidate also refuses while main changed one of the item's product files with other content (it would stop at SYNC_REQUIRED). See `docs/team-pack/13-workflow-toi-uu.md` §Item phụ thuộc item khác.
- Prepare does not wait for the worktree's dependency setup (2026-11-04, after EIOR38SI, where it held pickup 45–105 s): the fixer is spawned once the worktree, codegraph index and brief exist, and the brief's `<environment>` block has it wait with `job_status` for the setup job before its first build, test, migration or app start; the setup job retries once, and `worktree sync` waits for it. Answer-only TASKs (`answerOnlyTask`) get no install/generate/migrate/seed at all and load project packages from the installed main checkout. Other node worktrees without a `generate` step whose dependency files match the issued revision get linked node_modules instead of an install (2026-11-10, after QDYZMY1K, where the organizers' prepare-source in 6–7 worktrees at once took 5–13 minutes each; `pack/src/env/linked-modules.mjs`, switch `linkedModules`): junctions to the main checkout's packages, workspace packages mapped to the worktree's own `packages/`, no build. `git worktree remove --force` and `git clean -x` follow junctions and delete the main checkout's files, so every worktree removal calls `unlinkNodeModules` first.
- In GAME `configure_session` boots the match itself (login, backlog sync, poller, auto-prepare, company tool list; `boot`, switch `bootOnConfigure`), so root goes straight to `wait_for_update`; login_match/refresh_match only when `boot.ok` is false.
- Before that, `report_ready` starts a pre-game watch (2026-11-04, after CA3WKX60): the helper polls the match page every 500 ms without log lines, records `seenAt` and prewarms worktrees of visible items, but never Starts Work or writes DISCOVERED before START_GAME. In GAME the poller reads the page every 250 ms around each release minute from the README. Switches `preGameWatch`, `prewarmWorktrees`, `preGamePollMs`, `releasePollMs` (`docs/team-pack/13-workflow-toi-uu.md`).
- Root loops on `wait_for_update` (it carries `nextActions`) and nothing else: no `wait_agent` (2026-11-04, after BTZNI69E). In GAME it wakes only for `nextActions`, a match/item change or the 55 s cap. Workers never `send_message` root; they signal through `worker_checkpoint` (`ready_for_evidence`, `candidate`, `blocked {question}` → `answer_worker`), and root messages a worker only as a `followup_task` for a `nextActions` entry or a publish error. `nextActions` hides a `publish_item` the helper publishes itself and any item whose publish job is running. `prepare_item` and `publish_item` wait up to 25 s for their job.
- After WQ7T6CEC (2026-11-12): a wave waits until every item of its release minute has finished prepare, up to 90 s (`WAVE_GATHER_MAX_MS`; PIs used to get a wave of their own); the helper compares the files every live worktree changes and tells each worker once per change of the overlap set (`inFlightOverlap`, in the `analysis` field of `ready_for_evidence`, a warning at candidate); the analyst input has `<likely_files>` per item and the files earlier items changed so far; `run_checks {action: "mutants"}` answers `skipped` when the accepted profile states grading rules without `detection`; when the baseline owner's fix lands after an item synced, the item reruns only the baseline failures' test files plus its own new tests (`run_checks {checks: ["test"], testFiles}`, `baselineRerun`, `selected-tests.log`, a verification row that says it is not the full suite; the full suite only when the files cannot be placed). Profiles gained `zero_condition`/`evidence_rule` aspects, `minViewport` on evidence (PNG size checked at candidate) and `zeroConditions` (size limits, required files); `deadlineMinutes` was dropped, the deadline comes from the Game Master.
- PI speed, part 2 (2026-11-12, after DVVFEPXF PI-03, which closed unsubmitted): worktrees check out only the match folder (`git sparse-checkout`, mid-game prepare was 49–168 s because the team repo keeps every earlier match), `run_checks {action: "mutants"}` is skipped for a PI, a bulk `search_logs` lookup writes its file as soon as the asked queries are done (`onMain`, named in the job's progress) and probes past an id range in parallel batches, `catalogue: true` turns that extension off when the ids are the test-data catalogue, and the result part of `candidate` maps submit.json words (DONE, PASS, met…) to the fix-result enums (`normalizeResultPart`).
- A BUG/PI/CR handoff whose only non-answer changes are new tests (a reproduction without its fix) has those tests moved to `answers/<ID>/evidence/unshipped-tests/` by `worker_checkpoint candidate` (2026-11-10, after QDYZMY1K, where PI-03's red test on main cost BUG-09 and BUG-11 their team-tests points), and a PASS scenario lacking the evidence file its MVS requires blocks the handoff instead of only warning (QDYZMY1K BUG-11, −8).
- `worker_checkpoint candidate` waits for the item's running bulk `log_lookup` job (90 s) and refuses once while its result is unread (2026-11-10, after LXRMBRA2, where PI-03 handed off blank report fields 36 s before its lookup finished). Pushes have no file-size limit (TASK-07 must commit a 10 MB manifest; the old 5 MB check left its commit on local main and blocked BUG-11), and the push path checks run in `integrateCandidate` before the commit reaches main.
- Before handoff (2026-11-11, after EXP3I47A and YSKRYL4B): `backlog-references` has a six-question checklist for every item, and `worker_checkpoint candidate` enforces what code can check, each refusal once per state and only while time allows: a NOT_RUN scenario with 5+ minutes to return_by (`notRunGate`; EXP3I47A BUG-09 handed off three NOT_RUN scenarios with 23 minutes left after three captures on a profile spoilt by "Try Demo"), a BUG/CR/TASK that changed existing product code and added tests without `run_checks {action: "mutants"}` on its current source or with a change no new test catches (`mutantGate`, `pack/src/env/mutants.mjs`: undoes each hunk in turn and runs the new tests; EXP3I47A TASK-08's payee-after-rules case passed without the fix), and new files under `node_modules/` (YSKRYL4B CR-07 committed vitest caches). New lessons go into one of the checklist questions, not into another per-match note. A separate checker agent for hard, long items is approved but not built yet.
- Item analysis (2026-11-12, after BI7A5ACV, where the mutation check ran on 8 items although only TASK-08 grades detection; by wave since DVVFEPXF, where CR-08 reached main before CR-05 with CR-05's older files and CR-05's publish failed three times): a third profile, `pack/agents/team-analyst.toml` (strong tier, `gpt-6.1-sol`), reads ALL items of one release wave from `.team-work/waves/<wave>/analysis.md` and hands in one typed profile per item (`worker_checkpoint {phase: "profile", profile}`, `pack/contracts/item-profile.schema.json`) and one wave report (`{phase: "wave", wave}`, `wave-report.schema.json`: dependencies with quotes, shared files, landing order). `pack/src/match/profile.mjs` only checks them: schema, every quote word for word, scenarios equal to the template rows, real items. No worker waits for the analyst: `spawn_worker` and `spawn_analyst` (one per wave, offered once, one retry after 60 s; a wave closes when its prepares are done or 20 s after the first) come together. An accepted profile goes into the brief (`<item_profile>`, `<checklist>`), reaches a running worker once in the `analysis` field of the `ready_for_evidence` answer (`analysisNote`, with the wave's shared files) and feeds `checklistGate` at candidate (required evidence of a PASS scenario, answer fields, named source files; refused once). Dependencies of the report are added to `dependsOn` (only added), so the early copy of the fix works for them too. Switch `analyst`.
- Landing order (2026-11-12, after DVVFEPXF): an item that waits for another (`dependsOn`) holds its publish while that item is still in work and not on main, as long as it has more than two minutes above its last-call mark (`dependencyHold`). When the waiting item did land first, the waited-for item owns the files it shared: its publish no longer stops at SYNC_REQUIRED for them (`echoedFiles`), the helper syncs its worktree keeping its own version of those files (`worktree sync` `prefer`), records a new candidate from the same fix-result and submits, with a warning. A failed job keeps its `error {code, message}` in the journal (`recordJob`).
- Two groups of checks. Time-costly checks may be switched OFF by an accepted profile: today only the mutation check (`mutantGate` asks for it only when the profile has a `detection` grading rule, or when there is no profile or it states no grading rule). Safety checks never read the profile and always run: submit.json schema, test configuration, issued tests, `node_modules/`, secrets, paths outside the match, garbled text and reshaped timestamps. Keep new checks in the right group.
- The helper publishes every item type itself at handoff (`autoPublishAll`, default on; 2026-11-12): root sees `publish_item` only when that publish failed. With it off, only PI and answer-only items are published by the helper as before.
- Each item can be submitted only once. The helper trusts the worker's own tests and evidence (the user's choice on 2026-11-03, to keep the pack simple) and only reports what its answer/evidence checks find.

## After a practice match

`/judge-practice <match checkout>` (skill in `.claude/skills/judge-practice/`, scripts in `tools/judge/`) re-judges every item against `tools/judge/rubric.md` before reading the gate/reviewer verdicts (matches before 2026-11-03 still have them), then reports false greens/reds; bundles go to the gitignored `runs/judge/`. The same skill runs `tools/judge/usage.mjs`, which sums tokens, credits and run time per role, item and thread from the Codex transcripts (`~/.codex/sessions`, one file per thread, same `session_id` as root; the Player dashboard counts root and, since 0.9.41, subagents, but never the guardian auto-review threads) plus the helper journal (`jobs[].ms`, `endedAt`, `outcome`), into `<bundle>/_usage/usage.md`. Then `tools/judge/items.mjs`
rebuilds `runs/judge/_items/items.md` (+ `items.csv`): every match side by side and one row per item (judge, time per
phase, fixer model and turns, evidence capture failures, credits, flags to tune), and `tools/judge/bench.mjs` writes
`runs/judge/_items/bench.md`: matches grouped by item set, the newest of each set against the previous one of the same
set, per match and per item.
